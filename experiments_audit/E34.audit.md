### 1.4 Split and label alignment
- Line counts: en/de/fr = 11000 / 1000 / 5000 for train / validation / test — the **official** split.
- **Test rows are parallel**: `multi_hot` identical on all 5000 rows for en-vs-de and en-vs-fr
  (0 differing cells); per-document word counts correlate at r = 0.9992 / 0.9993.
- **Train rows are not parallel**: 47,930 (en vs de) and 47,683 (en vs fr) differing label cells out of
  231,000; word-count r = 0.003 / 0.014.
- **Validation rows are not parallel either**: 4,972 / 5,016 differing label cells; word-count r = 0.05 /

- No identical document text across train/validation/test (sha1 sets, all 9 pairs, zero intersection).
  There is no train/test contamination.

### 1.5 Does chunk pooling leak?
No label leakage. Chunk pooling is unsupervised: it reads only the document text at embedding time, the
same text the truncation baseline reads, and the target language is never given labels.
The only target-label-free use of test data is the `quantile_match_enval` threshold, which is a
transductive per-concept quantile of **target test scores** against **EN-val true rates**
(`quantile_match_thresholds`, lines 306-317, called with `test_scores` at line 386). This is by design and
identical for all schemes, so it cannot create the between-scheme differences; it does mean the reported
absolute F1 is test-distribution-adaptive.

### 1.6 Does pooling change the effective context?
Yes, materially, and the change is large even though the metrics are not:
- Context per document: 8.87 / 14.26 / 13.73 chunks on en / de / fr test = 4.7x / 7.4x / 7.1x the 512
  tokens the baseline sees. 94.5% (en test), 99.3% (de test), 99.2% (fr test) of tokens lie beyond chunk 1.
- The pooled vector really differs from chunk 0: cosine(mean, trunc) = 0.960 (en) / 0.970 (de) / 0.971
  (fr), min 0.47-0.53, and 2.1-8.5% of long documents fall below 0.9.
- For documents <= 512 tokens (32.3% of en test, 5.9% of de test, 6.8% of fr test) the schemes collapse
  **exactly**: `trunc == mean == max` (atol 1e-6) and `concat == [mean|max]` on every short row. Verified
  on all three test caches. Those rows dilute the comparison but do not invalidate it.
- Shortcut check that the null result is not a dilution artifact: restricting the evaluation to documents
  with > 512 tokens (3385 en / 4704 de / 4661 fr test rows), EN->de micro 0.6855 -> 0.6862 (AUC 0.8618 ->
  0.8648), EN->fr 0.6867 -> 0.6986 (AUC 0.8753 -> 0.8694), EN 0.6997 -> 0.7077 (AUC 0.8965 -> 0.8950).
  Same fitted model, same features, subset only. Still noise-level; AUC moves both ways.

### 2.5 The `trunc` baseline is not the E18 `emb_mean_*` array
`embed_docs` tokenizes once with `add_special_tokens=True` (line 167) and slices raw id windows
(lines 147-158). For a document with n > 512 tokens, **chunk 0 has no end token** and contains 512
content ids. `extract_embeddings.py:102` instead truncates to `MAX_LEN - 1 = 511` ids, i.e. 510 content
ids + EOS. The arrays therefore differ:

| cell | identical | cos mean | cos min | rel-L2 mean |
|---|---|---|---:|---:|
| en/test | no (1615/5000 rows exact) | 0.99975 | 0.98420 | 1.8e-2 |
| en/train | no | 0.99977 | 0.99438 | 1.7e-2 |
| de/test | no | 0.99936 | 0.99154 | 3.4e-2 |

Per-row check on en/test: the 1608 docs with <= 510 tokens are **exactly equal**, and 7 of the 9 docs with
exactly 511/512 tokens are equal too (a 511-token doc is not truncated); only the 2 docs with 512 tokens
and all 3383 docs with > 512 tokens differ. So the difference is fully explained by the missing EOS + the
extra content token.
Consequence: E34's `trunc` numbers are not a re-measurement of the published truncated pipeline; they are
a slightly *stronger* baseline (one extra token). This is a fair control, but it must be stated, and E34
cannot be used to claim "our 512-token baseline reproduces E18".

### 2.6 The split protocol differs from E18
E18 documents MultiEURLEX as *"re-split 10000/1000/5000, seed 0"* and says *"the official
`*_validation.jsonl` is not used"*. E34 uses **11000 train + the official 1000-row validation + 5000
test**. So E34's EN-self (micro 0.7433) is not comparable with E18's mel EN-self (0.717-0.718): different
train size, different validation set, different transform ladder. Neither doc says this.

### 2.7 Validation is not parallel, so the calibration prevalence is mismatched
`quantile_match_thresholds(test_scores, Y["en"]["validation"])` (line 386) sets each concept's target
predicted-positive rate to the **EN-validation** true rate. Because validation is not parallel to the test
set (1.4):
- mean prevalence EN-val 0.1754 vs EN-test 0.1711 (targets share the test prevalence exactly);
- mean per-concept |delta| = 0.0194, max 0.0698 (concept 17);
- **7 of 21 concepts** deviate by more than 20% relatively.
This over-predicts slightly for every language, so the EN-target *ratio* is still fair, but the absolute
F1 (and the "macro-F1 gap" headline) carries a per-concept calibration error of up to ~7 pp on one
concept.

### 2.8 The `.md` omits the chunk statistics and the gap-micro column

`chunk_stats` at lines 557-559. The MD is therefore generated before `chunk_stats` exists and has no

## 3. Bugs / risks

### 3.1 `--limit` without `--tag` overwrites the full result (high)
`out_json = ROOT / f"chunk_pool_mel{_TAG}.json"` (line 508) depends **only** on `--tag`. The embedding
caches are protected by the limit marker (`cache_suffix`, lines 202-204: `_TAG + _L{limit}`), but the
output is not. `python chunk_pool_mel.py --limit 200` (no tag, a very natural smoke invocation) writes
`chunk_pool_mel.json` / `.md` from 200 documents and destroys the 5.6 h result. Nothing warns, nothing
backs up, and the `.md` would carry the same "11000/1000/5000" header (2.3).

### 3.2 Embedding caches are not keyed by anything that affects the features (high)
`paths = CHUNK_DIR / f"{lang}_{split}_{s}{suf}.npy"` (line 210). `suf` is tag + limit only. Changing
`MODEL_ID`, `MAX_LEN`, `STRIDE`, or the pooling definition (lines 63-69, 224-230) silently reuses stale
features of the same shape and produces plausible-looking wrong numbers. `np.save` (line 232) overwrites
without backup, and the "if any cache is missing, recompute all four" branch (line 211) means one deleted
file re-embeds the cell and overwrites the other three.

### 3.3 `mean`/`max` pooling over overlapping windows is not a mean over the document (medium)
Stride 256 on windows of 512 means 50% overlap: every 256-token band at a window boundary is counted
twice by `a.mean(0)` (line 225). The pooled vector weights boundary tokens 2x relative to interior tokens,
and the effective weight per token depends on k (the chunk count), so documents are weighted differently
inside the same fit. `max` has the same structural issue (a max over overlapping, partially duplicated
windows). Neither is a token-level document representation, and the docstring's "mean pooling ... of the
document" overstates it.

### 3.4 Intermediate windows have no end token (medium)
Only the final window contains EOS; windows 1..k-1 are bare id slices. EuroBERT was trained with an
appended end token, so k-1 of k chunk vectors are produced out of distribution. This affects the pooled
schemes *and* the `trunc` baseline for long documents (2.5). Fixing it would change every number in the
table, so it is not a cosmetic issue.

### 3.5 `concat` is a dimension change under a fixed tree budget (medium)
`concat` is 1536-d trained with the same depth-8 / 400-tree / `colsample_bytree=1.0` budget (lines 71-75).
Its F1 moves are +-0.5 pp (2 of 4 cells above the baseline), so the pooling interpretation is ambiguous in
both directions: the extra 768 features and the doubled fit time (640-645 s vs 290-295 s) buy nothing, and
the deficit cannot be attributed to pooling rather than to an untuned 1536-d model.

### 3.6 The "gap" is measured against a moving ceiling (medium)
`gap = ceiling(scheme) - EN->target(scheme)` (lines 405-411) and `closure = gap(trunc) - gap(scheme)`
(413-419). The ceiling is refit in the same representation, so closure conflates "transfer got better"
with "the in-language model got worse". Example: de `concat` closure micro is -0.0041 even though its
ceiling moved up (0.7354 -> 0.7386). Report the raw deltas, or fix the ceiling.

### 3.7 The EN model is fitted 4 times per scheme (low, but ~1.2 h)
`fit_eval("en","en")` (line 379) then `fit_eval("en", tgt)` for `tgt="en"` (line 385) refit the same model,
and `en`, `de`, `fr` share one feature matrix. The log shows 6 fits per scheme x 4 schemes = **24 fits**,
of which **12 are redundant EN refits** (290 s each at 768-d, 640 s for concat): ~1.2 h of the 2.5 h
training stage is pure waste. Deterministic (`seed=0`, no subsampling), so no numeric effect.

### 3.8 `load_split` is called twice per cell (low)
Line 534 calls `load_split` again right after `build_representations` -> `load_split` (line 215), so every
90 MB jsonl is parsed twice for nothing (~10 s of the 20,084 s run, plus peak memory).

### 3.9 Status/PID side files are never cleaned (low)
`pid_path.write_text(...)` (line 512-513) is never removed, and the status JSON is left at `phase: done`
forever. `%TEMP%\opencode\chunk_pool_mel.pid` (PID 32736, 2026-10-11) and
`chunk_pool_mel_status.json` still claim a run; both PIDs are dead. Any "is it running?" check based on
these files is wrong.

### 3.10 Whole run is untracked and git-ignored (high, provenance)
`git ls-files` finds nothing; `.gitignore:72` (`chunk_pool_mel*`) ignores the script **and** the results,
and `.gitignore:68` ignores `multieurlex_chunk/`. There is no commit history for the script, no way to
diff the code state against the stored JSON, and the only surviving record of the run configuration is
`%TEMP%\opencode\chunk_pool_mel.log` (which the OS may clear).

### 3.11 Single seed, single split, no uncertainty (medium, inference)
No seed argument, no repeats, no CI. The 4 schemes differ by 0.9-1.6 pp macro-F1 while a 150-doc smoke
run flipped the de gap negative. At this effect size the comparison cannot distinguish "no effect" from
"small effect", which is exactly what the verdict claims.

### 3.12 Long-document spike (low)
One de test document is 390,984 tokens -> 1527 windows -> a 1527 x 768 `float32` block for one document,
and `per_doc` duplicates the whole `emb` array (line 198 copies views). Peak RAM is roughly 2x the chunk
matrix (277 MB for de/train, more for the pooled cells). It survived, but the code has no cap and no
guard.

### 3.13 `.md` cannot be regenerated without a 2.5 h retrain (medium)
There is no `--render`-style path (compare E18). `--skip-train` returns before writing anything
(lines 550-553), so once the JSON exists, fixing a typo in the markdown means refitting 24 models (2.5 h).

## 5. Recommended changes

Not applied — this is an audit. Ordered by risk.

1. **Guard the output path.** Make the default output include the limit (`chunk_pool_mel{_TAG}{_L{limit}}.json`)
   or `sys.exit` when `--limit` is given without `--tag` (line 496-509). This is the only change that
   prevents silent destruction of the 5.6 h result.
2. **Key the caches by the feature definition.** Put `MODEL_ID`, `MAX_LEN`, `STRIDE` and the pooling
   version in the filename or in a `cache_meta.json` that is checked on load (lines 202-213). Same for
   `stats.json`.
3. **Write a verdict into the MD and generate it after `chunk_stats` exists.** Move `write_markdown` after
   the `chunk_stats` re-write (lines 557-559), add a chunk-stats table, add `gap micro`, and state the
   conclusion: *pooling moves F1 by <= 1 pp and moves AUC negatively; the EN->target gap is not closed.*
   The current artifacts contain no conclusion, and the log's "best scheme = mean" reads as a win.
4. **Fix the docstring.** Remove `--force-train`, state that training always re-runs, and change the smoke
   example to `--limit 150 --tag _smoke` (the command that actually produced the stored smoke).
5. **Stamp the sample size.** Put `n_docs`/`smoke: true` into the JSON and a "SMOKE (150 docs/split)"
   line into the MD header; the current smoke file is indistinguishable from the full run.
6. **Quarantine or regenerate the smoke artifacts.** They do not reproduce (2.2) and their numbers are
   noise (2.3). Either regenerate with the current code and keep them as a regression test, or move them
   out of the repo root. Delete the 12 orphan `*_smoke.npy` caches.
7. **Give intermediate windows an end token**, or state in the docstring that only the last window carries
   EOS. Then re-run at least the `trunc` and `mean` schemes so the baseline and the pooled schemes are on
   the same footing (this changes every number).
8. **Report raw deltas next to gap closure**, or hold the ceiling representation fixed (3.6).
9. **Add 3 seeds** (or bootstrap the 5000 test rows) before any "1 pp improvement" claim. 300-640 s per
   fit makes 3 seeds x 2 schemes ~3 h; 4 schemes x 3 seeds is ~7 h and probably not worth it.
10. **Add a dimension-matched control for `concat`** (e.g. `mean` duplicated to 1536-d, or a tuned
    `concat`), otherwise the 1536-d result is uninterpretable.
11. **Un-ignore the script** (`.gitignore:72` currently hides `chunk_pool_mel*` including the `.py`) and add
    the E34 entry to `EXPERIMENTS.md` with the split difference from E18 (2.6) spelled out.
12. **Drop the double `load_split`** (line 534) and the redundant EN refits (lines 379-385) — ~1.2 h saved
    with zero numeric effect.
13. **Document the truncation asymmetry** in the entry: EN loses 94.5% of its tokens to truncation,
    de/fr lose 99.2-99.3%. It is the strongest argument that the null result is not an artifact.
