# E40 audit — legacy pre-E18 XGBoost suite (FLORES topic, SST-2, emotion)

**Scope.** `xgboost_topic_optuna.py`, `xgboost_infer.py`, `xgboost_sst2.py`,
`xgboost_emotion.py`, `xgboost_flores_{lang,combined,matrix,drop_optuna}.py`; the four surviving
trial CSVs; the deleted result artifacts (recovered read-only from git at `aa3f6f6`); README /
REPORT / EXPERIMENTS / COVERAGE claims about them. No repo file was modified: every re-run either
read cached arrays or wrote only under `%TEMP%\opencode\`. Thread caps were 2
(`OMP/MKL/OPENBLAS_NUM_THREADS=2`, `n_jobs=2`), CPU only, no launched windows.

**Verdict.** The suite is **deterministic and, in the parts tested, exactly reproducible** — but only
against the **2009-row FLORES CSV that no longer exists in the worktree** (`aa3f6f6`; `196bbd3` has
the same row count but relabelled topics). Against the current 2006-row CSV **every entry point
aborts** at `assert len(df) == 2009`, so "NOT AVAILABLE" is the correct standing for the published
tables even though the numbers themselves check out. Verified exactly: EN/`mean` per-mode table
(4 rows × 3 metrics), its transfer rows and thresholds, label counts, the `mean` column of the
per-language grid (en/it/de), the SST-2 `mean` row, the emotion `mean` row, and the four embedded
inference param sets. Not verified: all Optuna searches, the `fr`/`bos`/`eos`/`lead` grid cells, the
drop-dim ablation numbers, the strict-label table (now unreproducible), and every 0.975-style claim
(none exist — see §6).

## 2. Discrepancies

1. **"Deleted and not retained" is true of the worktree, not of git.** The published tables are
   recoverable read-only at `aa3f6f6`. That does not make them verified — but any future reader can
   re-derive them, so the entry should say "archived at `aa3f6f6`" rather than implying loss.
2. **Data sizes in the README disagree with the shipped CSVs.** `README.md:21` says `sst2.csv` is
   68,221 rows (67,349 train / 872 validation); the file is **54,577 / 6,822 / 6,822** (80/10/10
   re-split, commit `397281b`), which `README.md:265` states correctly. `README.md:22` says
   `emotion.csv` is 18,000 rows (16,000/2,000); it is **20,000** (16,000/2,000/2,000 test).
3. **`xgboost_sst2.py:11-13` docstring is stale** for the same reason ("train 67,349 rows … validation
   872 rows"). The code path (`load_sst2`) reads the re-split CSV, so the docstring misdescribes the
   run that produced the shipped numbers.
4. **"~504/2009" all-zero rows** (`README.md:193`, script docstring `:44`) vs the verified **515**
   (also what the archived table itself prints). The script's own reference constants disagree with
   reality: `AUDIT_LENIENT_TARGETS` (`:166-169`) match the verified counts exactly, but
   `AUDIT_LENIENT_ZERO_ROWS = 504` (`:170`) is 11 low, so `_report_lenient_counts` prints
   `delta=+11` on every run. Cosmetic (it is a log line, not a gate), but it is the kind of number a
   reader will check.
5. **The strict-label table (`README.md:242-253`) cannot be regenerated at all.** Its source
   (`aa3f6f6:xgboost_topic_allmodes.md`) is archived and matches the README character-for-character,
   but `load_data("strict")` now aborts at `assert (Y[devtest_mask].sum(axis=0) > 0).all()`
   (`xgboost_topic_optuna.py:254`): under exact-string labels at least one tag has zero devtest
   positives. The table is also built on the 2009-row CSV and its Optuna objective was the test split
   (archived text: "score macro-F1 on `test`"). It is a dead code path, not a slow one.
6. **Two split conventions coexist.** This suite uses 997/506/506; `train_flores12.py` (E18, E21, E42)
   uses 997/504/505. Both appear in `README.md` without a warning that the numbers are not
   comparable across sections.
7. **The published test metrics of the transfer arm have no valid English denominator.** The arm
   trains on all 2009 EN rows (`:482-489`) and prints `en (in-sample) 1.0000`; the archived notes say
   it is an upper bound. Any target/English ratio built from that row would be an artifact.
8. **Drop-ablation numbers are asserted without any surviving artifact.** `README.md:220-221`
   (0.5093 / 0.3585 / 0.4773 / 0.2911) rest on `xgboost_flores_drop_optuna_status.json` and the
   `models/flores_{lang}_{mode}_drop50_optuna` bundles — neither exists (`models/` contains only
   `flores12_*` bundles and GGUF files). `models_registry.json` has no entry for them.
9. **Archived artifacts reference a file that no longer exists**: `audit_labels.md` (deleted at
   `f768fb8`) is cited by `xgboost_topic_optuna.py:44`, `:86`, `:110` and by the comment above
   `AUDIT_LENIENT_TARGETS` (`:165`), as well as by every archived table.
10. **`xgboost_perlang_lenient_pertopic.md` (per-topic accuracy, README:206-207) has no producer left
    in the tree**: `pertopic_accuracy.py` / `pertopic_accuracy_transfer.py` were deleted at
    `f768fb8`. The per-topic claims are unverifiable.

## 3. Bugs / risks

1. **Test-set hyperparameter selection in `run_mode` (`:421-442`).** The Optuna objective is
   `test` macro-F1 and the same test split is then reported. Every `xgboost_topic_results_*` and
   `xgboost_topic_allmodes*` number is therefore a selection-set score (the archived note says so;
   the README table does not). The four param sets embedded in `xgboost_infer.py` inherit that
   optimism.
2. **Transfer models see the test rows.** `:482-489` fits on `all_mask` (2009 rows) for the EN→target
   arms, so those predictions are partly in-sample; the printed `en (in-sample)` row is 1.0000 by
   construction.
3. **Hard-coded 2009 asserts break every entry point on current data** (`:230`, `:272`, `:932`). The
   failure is a bare `AssertionError` with no hint that `196bbd3`/`aa3f6f6` is required. Confirmed by
   running `xgboost_infer.py` against HEAD data.
4. **The lenient relabelling of 2026-10-05 silently changes the task.** Using the 2009-row `196bbd3`
   CSV with current code yields 469 all-zero rows and per-tag totals 518/137/122/125/71/90/391/97 —
   i.e. a *different* label distribution from the archived 515 and 518/148/121/177/81/117/317/151.
   Only the pre-`00d4823` CSV reproduces the published counts. Anyone "restoring the 2009 CSV" from
   `196bbd3` will silently reproduce something else.
5. **In-sample threshold tuning collapses to the grid floor.** On the EN/`mean` baseline, tuning on
   dev+devtest predictions returns `[0.05 × 8]` (the lowest grid point), because a 300-tree booster
   is near-separating on its own training rows. The "tuned" rows are consequently optimistic and
   threshold-dependent in a way that has nothing to do with test behaviour.
6. **Thread budget regression.** `xgboost_sst2.py:27,296` and `xgboost_emotion.py:31,333` default to
   `--threads 4`; only the FLORES scripts hard-pin 2. A default re-run exceeds the 2-thread rule, and
   the embedding stage also uses the GPU.
7. **Trial logs lose a recorded metric.** `xgboost_sst2.py:202-203` sets a `macro_f1` user attribute
   but `save_trials` (`:216-225`) writes only `value_accuracy`; emotion writes `value_accuracy` for an
   AUC objective. The macro-F1 / accuracy columns seen during the search are unrecoverable.
8. **`xgboost_flores_drop_optuna.py:232-237`**: the failure handler writes a *fresh* status dict
   (`{"pid":…, "state":"failed", …}`), overwriting per-cell progress and results. A crash at cell 4
   destroys the evidence of cells 1–3 in the only file that records them (the bundles would survive).
9. **`xgboost_flores_{lang,combined,matrix}.py` evaluate on the rows they train on** (all 2009, or
   dev+devtest); they report in-sample numbers under names like "en in-sample", which is honest, but
   the scripts are cited as EN/IT reference results where a held-out number would be expected.
10. **No repeated seeds anywhere** in this suite; a single seed per cell, and the per-tag thresholds
    are tuned on ≤1503 rows. Selection noise is unquantified (the archived `devtest → test` shifts of
    +0.04 to +0.08 suggest it is material).
11. **No persisted topic models.** `xgboost_infer.py` retrains 8 tag models per invocation (~30 s at
    the measured 23 s for the transfer fit); the only persisted artifacts from this suite
    (drop-ablation bundles) are gone.

## 5. Recommended changes

1. **State provenance in E40 and in `README.md`**: numbers are from the 2009-row / 8-tag / 506-506
   era, archived at `aa3f6f6`, and are reproduced only against that CSV. Link the archive instead of
   leaving the reader with "outputs deleted".
2. **Fix `README.md:21-22`** (54,577/6,822/6,822 for SST-2; 20,000 for emotion) and the stale
   `xgboost_sst2.py:11-13` docstring.
3. **Make the data requirement loud**: replace `assert len(df) == 2009` with a message naming the
   required CSV revision, or align by `id` and drop the 3 removed rows — but note that row alignment
   alone is *not* enough (bug 4), because the label strings changed.
4. **Retire the strict-label path** (`README.md:242-253`) or relax the devtest-nonempty assert for
   strict labels; as it stands the documented command cannot run.
5. **Do not reuse the `--mode all` numbers as results**; they are test-selected. If `xgboost_infer`'s
   embedded params stay, label them "selected on the test split" in the script docstring.
6. **Restore `audit_labels.md`** (or strip the references from the docstrings), since both code and
   archived tables cite it.
7. **Set `--threads` default to 2** in `xgboost_sst2.py` / `xgboost_emotion.py` to match the repo's
   compute budget.
8. **If any of these cells are quoted again**, quote the verified ones with their provenance (EN
   `mean` per-mode, SST-2 `mean`, emotion `mean`, `mean` column of the grid) and mark the rest
   UNVERIFIED; do not resurrect the drop-ablation figures without their status JSON or bundles.
9. **Write a note in `EXPERIMENTS.md` E3/E4** pointing at this suite: E3/E6/E7's scripts never existed
   in git, and E4's `crosslingual_sentiment.py` is missing; `xgboost_sst2.py`/`xgboost_emotion.py` are
   EN-only and do not substitute for them.

## 6. The 0.975 bar

**N/A.** No retained target/English ratio exists for this suite. The EN reference available here is
trained on all 2009 rows including the test rows (in-sample 1.0000), and the per-language grid
compares in-language models rather than EN→target transfer. No ratio should be reconstructed from
these tables; the 0.975 question is answered by E18 (`proof_mean_alllangs.py`, 0/8 cells).
