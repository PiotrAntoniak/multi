## Verified

1. **`mel_close.py` is the surviving 210m implementation and its artifacts are internally
   consistent.** `mel_close.json` config says `emb_model = EuroBERT/EuroBERT-210m`, `dim = 768`
   (`mel_close.json`, config block). `mel_close.md` rows equal the JSON rows (raw 0.3429/0.4637,
   `l2_thenZ` 0.6430/0.6405, ensemble 0.7276/0.7100, ceiling 0.4372/0.4596). `mel_close.log` shows a
   single 1877 s run with `tr=10000 val=1000 test=5000`, and the per-method lines match the JSON. The
   script and all three artifacts are committed unchanged (`git status` clean; only `21ab888` touched
   `mel_close.py`).
2. **The script still runs.** `python mel_close.py --smoke --outdir <temp>` exited 0 in 43.5 s with
   `n_jobs=2`, wrote JSON/MD/PNG/status to the temp dir, and reproduced the same structural behavior
   (including the near-chance ceiling).
3. **Split/leakage facts were measured directly.** `en/de/fr_test.jsonl` are 5000 rows each with
   identical `multi_hot` row-for-row (5000/5000 for de and fr). `en_train.jsonl` vs
   `de_train.jsonl` agree on only 169/11 000 rows and vs `fr_train.jsonl` on 183/11 000 — i.e. the
   train splits are not parallel, exactly as `imbalanced_recall_mel_v2.md:3` and
   `imbalanced_recall.py:318-323` state. Only test is parallel.
4. **210m embeddings and labels load cleanly.** `multieurlex/emb_mean_*` are `(11000,768)` /
   `(5000,768)` float32, finite on sampled rows. `multieurlex_610/` are `(11000,1152)` /
   `(5000,1152)` float32.
5. **The E9 210m `raw` row is a fixed-0.5 threshold number.** `proof_mean_alllangs.json` (E18, same
   10k/1k/5k split, different script) gives raw de/fr micro = 0.2559/0.3413 at threshold 0.5 and
   0.3192/0.4459 at its tuned threshold 0.32. E9's 0.266/0.334 matches the 0.5 numbers, while
   `mel_close.json`'s 0.3429/0.4637 matches the tuned threshold (t=0.34).
6. **E16's 210m English-trained numbers are the `mel_close` ones.** The old E16 table
   (`21ab888:EXPERIMENTS.md`) lists raw 0.343/0.464, `l2_thenZ` 0.643/0.641, translate-train
   0.716/0.707, ensemble 0.728/0.710, EN self 0.742 — all present in `mel_close.json`. So E16's
   English-trained side is reproducible. Its "true native ceiling 0.714/0.712" is not.
7. **The 610m run is plausible but not evidenced.** `lang_matrix.md:106-138` (610m, same
   `perlang_z`, depth 8 / mcw 5 / 400, threshold 0.5, per-language train labels) gives mel EN-self
   macro 0.600, EN->de 0.371, EN->fr 0.449, native de 0.567, native fr 0.562, AUC 0.889/0.891. The
   E9 610m EN-self macro 0.601 and native macro 0.546/0.545 are in the same range, so the numbers
   are not implausible. `lang_matrix.json` stores no micro-F1, so the claimed 0.711/0.707 micro and
   AUC 0.872/0.875 cannot be confirmed.

## Discrepancies

1. **E9 210m `l2_thenZ` + calib 0.688/0.683 is not reproduced.** Every surviving artifact is lower:
   - `mel_close.json`: 0.6430/0.6405 (tuned global threshold), 0.6611/0.6616 (quantile matching).
   - `proof_mean_alllangs.json` (E18, independent script): perlang_z 0.6511/0.6518 (tuned),
     0.6695/0.6667 (qm).
   The old E9 write-up says the 0.688/0.683 came with **depth 8 / mcw 5** (the E15 v2 recipe adds
   400 trees), whereas the committed `mel_close.py` defaults to **depth 6 / mcw 1 / 200**
   (`mel_close.py:120-122`). The CLI exposes `--max-depth`/`--n-estimators` but not
   `min_child_weight`, so the E9 row cannot be reproduced exactly without editing the script. This is
   a config drift, not a small rounding gap (1.6-4.5 pp). There is also a split-size mismatch: the
   claimed ceiling source (E15 v2) uses the full 11 000 train rows
   (`imbalanced_recall_mel_v2.json` config: 11000/1000/5000), while `mel_close` holds out 1 000
   (10 000 train); E18 matches `mel_close` at 10 000. Numerator and denominator may therefore use
   different training-set sizes.
2. **E9 210m `raw` 0.266/0.334 vs `mel_close.json` 0.3429/0.4637.** Explained by threshold:
   fixed 0.5 vs EN-val-tuned 0.34. The E9 table does not state the threshold, so the two rows are
   not comparable as printed.
3. **E9/E16 "in-language ceiling" 0.714/0.712 is not in any JSON.** `mel_close.json`'s own ceiling is
   0.4372 (de) / 0.4596 (fr) micro with AUC 0.4697 / 0.5228 — near chance, because it was trained on
   the wrong labels (see Bugs). The 0.714/0.712 numbers appear only as prose in
   `21ab888:EXPERIMENTS.md` (E9 and E16), where E16 says they come from "independent verification
   (E15 mel v2)". `imbalanced_recall_mel_v2.json` contains only the eight rare-concept blocks
   (`results.13/16/14/9/11/10/20/8`) and **no overall micro/macro**; `imbalanced_recall_mel_v2.md`
   reports only rare-concept recall metrics. There is therefore **no artifact** for 0.714/0.712.
4. **E9 610m 0.711/0.707 has no artifact.** It exists only as text in the initial commit's E9 block
   (`21ab888:EXPERIMENTS.md`: "610m + `l2_thenZ` + `quantile_match` (FINAL): de 0.711/0.546/AUC 0.872,
   fr 0.707/0.547/AUC 0.875 vs EN self 0.752/0.601/0.910"). No `multieurlex_*` output was ever
   committed; `git log --all -- "*multieurlex*"` is empty and
   `git rev-list --all | git ls-tree` finds no such path. The current `multieurlex_610/` caches were
   written **after** the claim (2026-10-12 12:46-16:19 vs commit 08:05), and no script reads that
   directory (`backbone_grid.py:93` says it never touches it). The 610m row is **UNVERIFIED / NOT
   AVAILABLE**.
5. **E16 alias is dangling.** `REPORT.md:109` and `REPRODUCE.md:62` call `mel_close.py` "E16", but
   the current `EXPERIMENTS.md` has no E16 heading (grep returns nothing). E16's content survives
   only in `21ab888:EXPERIMENTS.md` and in the E9/E10/E11 block.
6. **REPORT's "de 0.93 · fr 0.93" micro ratio is from the `qm` metric, not the headline micro-F1.**

8. **The old E9 write-up's 610m EN self (0.752/0.601/0.910) cannot be checked against any surviving

## Bugs / risks

1. **Native ceiling is trained on English labels (critical).** `mel_close.py:719` does
   `fit_ovr(TX[tf][lg][tr], Ytr[tr], ...)` for `lg in ("de","fr")`: target-language embeddings with
   **English** train labels. Since train splits are not parallel (169-183 of 11 000 rows match), the
   labels are wrong. The result is the near-chance ceiling in the JSON (AUC 0.470/0.523; macro
   0.138/0.167). This is the same v1 bug documented in `imbalanced_recall_mel_v2.md:3` and fixed in
   `imbalanced_recall.py:315-325`; `mel_close.py` never received the fix.
2. **Native-ceiling threshold is tuned on mismatched rows.** `mel_close.py:722` passes
   `Ytr[val]` (English labels for the val row IDs) with `S_val` from the target-language model on
   those same row IDs. Because train rows are not parallel, the target val embeddings are different
   documents from the English val labels. Even if bug 1 were fixed, the threshold would still be
   wrong.
3. **`mlp_align` is invalid by construction.** `mel_close.py:664` fits `mlp_fit(Xt[tr], Xall["en"][tr])`,
   pairing de/fr train rows with English train rows that are different documents. The resulting
   AUC 0.4897/0.4764 (below chance) confirms it. The docstring's premise ("row i is the same document
   in every language", `mel_close.py:16-17`, repeated at `:824`) is false for train.
4. **Test-set selection in the ensemble and kNN.** `best_k` is chosen by mean **target test** micro-F1
   (`mel_close.py:626-629`); the ensemble's top-3 members are ranked by **target test** micro-F1
   (`:734-737`); the report's "best method" is also chosen by test gap (`:772`). The ensemble and
   `knn_best_k` numbers are therefore optimistically biased. Use EN-val or a nested split for
   selection.
5. **Transductive quantile matching.** `mel_close.py:389` sets each concept's threshold from the
   target **test** score quantile. It uses no target labels, so it is not label leakage, but it
   assumes access to the whole target test batch and is not a per-document deployable rule. It is
   also the source of the higher `qm` numbers (0.661/0.662 vs 0.643/0.641).
6. **translate-train depends on an unbuilt external cache.** `mel_close.py:678-709` loads
   `%TEMP%\opencode\tt_cache\mt_emb_mel_{de,fr}.npy`; no repo script creates them (grep for
   `mt_emb_mel` finds only `mel_close.py`). The caches currently exist (2026-10-11 10:02/10:14), but
   they are temp-only. If absent, the run logs "SKIPPED" and the ensemble silently changes to
   `knn_k20 + knn_k10 + l2_thenZ`.
7. **Config drift from the documented fixed recipe.** `mel_close.py:120-122` uses
   depth 6 / mcw 1 / 200 trees; `REPRODUCE.md:90-92`, E15 v2, E18 and `lang_matrix.py:157-158` all use
   depth 8 / mcw 5 / 400. The comment at `mel_close.py:118` calls its params "the FLORES-winning
   one-vs-rest config", which is not the config in `REPRODUCE.md`. Results are therefore not directly
   comparable across E9/E16/E18/lang_matrix.
8. **Metric ambiguity.** The E9 table has one column per language but mixes threshold conventions
   (fixed 0.5, tuned global, quantile-matched) and possibly two XGB configs. Without per-row metric
   and threshold labels the table cannot be checked.
9. **Small-sample / label imbalance.** 5 000 test documents, 21 labels, heavy imbalance (label counts
   range 57 to 2 769); micro-F1 is dominated by frequent concepts, while macro-F1 is noisy. Single
   seed, no CIs.
10. **`mel_close.py` rewrites its outputs in place in the repo root** (the docstring calls them
    "create-only", but `mel_close.py:601` opens the JSON with mode `"w"`). A rerun overwrites
    `mel_close.json/.md/.png`; there is no run tag by default (`--tag` exists). The committed JSON is
    the only baseline, so an accidental rerun with different params would destroy the evidence.
